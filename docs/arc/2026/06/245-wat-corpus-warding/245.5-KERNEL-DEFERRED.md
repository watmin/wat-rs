# Stone 245.5 — the `kernel/*` family DEFERRED (not warded) → arc 170

**2026-06-04. The 7 kernel files are NOT warded — deferred wholesale to arc 170.** Builder direction: *"170 will handle the kernel then — we're just marking territory as best we can."*

## The family

`wat/kernel/{channel,hermetic,run_threads,sandbox}.wat` + `wat/kernel/services/{stdin,stdout,stderr}.wat` — the concurrency infrastructure: thread spawn/join, channels, sandboxed execution, and the stdio service-loops. This **is** the arc-170 layer (the branch we're on is `arc-170-gap-j-v5-deadlock-state`; arc 170 is the program-entry/stdio-trio/spawn-fork reshape that closes the thread/process leaks).

## Why deferred (circumspicere triage, 245.5)

The ward bar is `deftest-green(<name>)` — a file's OWN forms exercised by a NAMED, **deterministic**, currently-green deftest. Every kernel file fails it, two ways:

- **`channel.wat` — typealias-only.** 7 `:wat::core::typealias` forms (Sender/Receiver/Channel/CommResult/Chosen/Thread|ProcessPanics); the actual `make-bounded-channel`/`send`/`recv` are Rust in `src/comms/`. A typealias is checked at load, never *run* — there is nothing for a deftest to exercise. (It is wardable *in principle* as a checker-clean type-definitions file, but the builder folded it into the kernel-goes-to-170 call rather than split it out.)
- **The other 6 — arc-170-leaky.** hermetic/run_threads/sandbox/stdin/stdout/stderr are inherently fork/spawn/drain/join. Their only coverage is the **excluded leaky ambient set** (`wat-tests/kernel/services/ambient-stdio.wat`: forks a child, 15000ms time-limits), which the green-gate `--lib` RUN deliberately excludes (`green-gate.sh:22-29`). The "greens" I first saw (hermetic 1 / stdout 1 / stderr 2) were FALSE — they live in that excluded leaky suite. No deterministic single-process test of their own forms exists or is honestly constructible; a contrived handler-only test (bypassing the spawn) would test a fragment, not the file's behavior.

Stamping any of them now would be the lying-certificate the whole arc exists to prevent.

## The call

**The kernel is arc-170's domain.** When 170 closes the thread/fork leaks and the gate can add the full `--workspace` RUN, the kernel becomes wardable — and channel gets its checker-clean type-file treatment then, as part of 170's kernel work. Until then: no kernel stamps; this is deferred-by-design, not a gap. (An unwarded file is a defect only when it's a live keepable member the arc *could* ward — arc 244; an arc-170-blocked concurrency file is not.)
