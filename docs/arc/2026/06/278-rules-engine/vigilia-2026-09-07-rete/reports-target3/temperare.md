### Findings

**1. `run-axis.sh` — asymmetric harness overhead inside the wall-clock bracket it uses to compute `:wall-ratio`/`:fire-share-pct`. Corrupts a measurement, ranked first.**

- `file:line`: `run-axis.sh:154-165` (the `guard()` wrapper), used at `:237`; contrast `:264`.
- Pattern: work-inside-a-timed-region (asymmetric between the two arms being compared).
- The wat side's wall-clock bracket is `WAT_W0=$(date +%s%N)` (`:236`) … `guard "$WAT_BIN" "$WAT_SRC"` (`:237`) … `WAT_W1` (`:239`). `guard` is either `systemd-run --user --scope --quiet -p MemoryMax=... -- timeout ...` or a `( ulimit -v ...; exec timeout ... )` subshell (`:154-165`) — in both branches, real process-spawn overhead (a D-Bus transient-scope creation for the systemd path, or an extra fork+exec for `timeout`) sits *inside* the measured wat wall-clock window.
- The Clara side's identical bracket (`CLARA_W0` `:263` … `clojure -Sdeps "$CLARA_DEP" -M -m "$AXIS"` `:264` … `CLARA_W1` `:265`) has **no equivalent wrapper** — no `guard`, no `timeout` at all. It is invoked bare.
- Consequence: `WAT_WALL` (`:366`) is inflated by scope-creation overhead that `CLARA_WALL` (`:367`) never pays, and both `WALL_RATIO` (`:368`) and `FIRE_SHARE` (`:376`, which divides `WAT_MEAN` — the clean, self-timed fire-only figure — by this same inflated `WAT_WALL`) are computed from that asymmetric pair. Both fields are advertised in the file's own header (`:26-36`) as a real, load-bearing signal ("An engine can win the fire and lose the program, and collapsing them hides exactly that").
- Dimension that grows: n/a in the scaling sense — this is a fixed per-invocation tax, so its *relative* distortion is worst on small/fast axes (where wall time is itself small) and shrinks as wall time grows, meaning it is largest exactly where `:wall-ratio`/`:fire-share-pct` are most delicate to read.
- Estimated cost: this is an estimate, not a measurement (I ran nothing) — a `systemd-run --user --scope` D-Bus round trip is commonly tens of milliseconds; against axes whose wat-wall is small this is not rounding noise for a wall-clock comparison.
- **What is NOT affected**: `:ratio`/`:winner` (the primary, gated verdict `check-grid-speed.sh` uses) are built from `:native-ns`/`:clara-ns`, both self-timed *inside* the respective program via `(:wat::time::now)` / `System/nanoTime` around `fire-rules` only (`accum.wat:209-213`, `gen-accum.sh:74-79`, etc.) — those numbers are clean of this asymmetry. Only the *secondary* wall/fire-share pair is corrupted.
- Tempered direction: wrap the Clara invocation in the same `guard` (or an equally-costed no-op wrapper) so both sides pay identical harness overhead, or move the guard's overhead out of the timed window on the wat side (spawn the scope, then start the wall timer once inside it).

**2. `check-where-shapes.sh` (and, smaller, `check-query-compat.sh`) — a JVM boot repeated once per corpus item, though the file's own header (and a sibling file's header, quoting it) asserts it happens exactly once. Pure waste — this gate reports no ratio/timing at all, so no number is corrupted, but the CI cost is real and recurring.**

- `file:line`: `check-where-shapes.sh:103` (`clojure -Sdeps "$CLARA_DEP" -M "$clj"`), inside `check_pair()` (`:90-133`), invoked once per discovered pair by the loop at `:140-150` (specifically `:149`). 38 pairs on disk today (counted: `for f in where-*.wat; do stem=...; [ -f "$stem.clj" ] && echo "$stem"; done | wc -l` → 38), so this is **38 separate JVM boots** per run of the script.
- The file's own header directly contradicts this: `check-where-shapes.sh:17-23` — *"run-axis.sh spawns one process per cell... a 200-row corpus would have spent ~37 minutes booting a JVM 600 times. Here the JVM tax is paid ONCE no matter how large the corpus grows. Measured at 6 rows: wat 0.22 s + Clara 3.7 s, against ~67 s for the same six through run-axis.sh."* That claim is quoted and generalized in the sibling file at `check-grid-three-way.sh:29-32`: *"38 families through a per-row runner cost ~67 s for six of them and **3.7 s for all thirty-eight in one JVM**."* Neither statement matches the code: there is no batching in `check-where-shapes.sh` — each pair gets its own `clojure -Sdeps` process.
- `git log --follow` on the file shows why: the "paid ONCE" text was written at commit `30d15b441`, when the corpus was a single `where-shapes.wat`/`.clj` pair with 6 rows inside it — at that point the claim was literally true (one file, one JVM, N rows inside it). Commit `c8b062e64` ("the where-corpus becomes one pair per family, discovered not listed") then refactored the single file into 38-and-growing discovered pairs, moving the single `clojure` call into a per-stem loop — but left the header's "paid ONCE" claim standing unchanged (confirmed via `git show c8b062e64` diff: the header hunk above the refactored code is untouched). `check-grid-three-way.sh` (committed later, and which *does* correctly implement the one-JVM pattern via its `STAGE`+`drive.clj` batching at `:198-223`) then cited the stale claim and generalized it to "38... in one JVM," which was never true of the code it was describing.
- `check-query-compat.sh:90` has the identical shape — `clojure -Sdeps` called once per stem inside `check_stem()`, invoked from the loop at `:130-133` — currently 3 stems (`where-query-compat`, `where-query-params`, `where-fact-bind`), so 3 boots instead of 1. Smaller in absolute magnitude today, but the same defect, and the corpus can only grow (it is discovered, not listed).
- Both scripts run in CI: `ci.yml:248` (`check-where-shapes.sh`) and `:254` (`check-query-compat.sh`) — confirmed by grep — so this is not a theoretical cost, it is paid on every CI run.
- Dimension that grows: n = number of `where-*` families (currently 38 for shapes, 3 for query-compat), and the corpus is explicitly designed to grow by discovery (`check-where-shapes.sh:39-41`: "a new family is two new files and nothing else").
- Estimated savings: order of magnitude, not measured — the files' own cited numbers (~3.5s JVM boot each vs. ~3.7s total for a batched run) imply roughly a 30-35x reduction in `check-where-shapes.sh`'s Clara-side wall time is available by adopting the exact "stage everything, one `drive.clj`, one JVM" pattern `check-grid-three-way.sh:198-223` already implements in the same directory for the same class of problem.
- Tempered direction: hoist the JVM boot out of the per-pair loop — stage all 38 (or 3) `.clj` files into one temp dir and drive them through a single `require`+`-main` loop inside one `clojure` invocation, mirroring `check-grid-three-way.sh`'s `drive.clj`. Also correct or delete the "paid ONCE" claims in both headers, since they currently describe code that does not exist.
