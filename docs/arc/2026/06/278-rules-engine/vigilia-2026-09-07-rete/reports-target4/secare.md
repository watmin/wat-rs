### 2. Process-structure ruling — corrected

The brief's binary-boundary framing (100 separate `tests/rete` binaries vs. one shared `src/rete/kernel/tests` lib-test binary, `mod.rs:43-44`) is **true as a compilation fact** but **not the operative mechanism for runtime parallel-safety**. Nextest — the repo's sole release-floor gate (`wat-rs/CLAUDE.md`: *"weighed in RELEASE … `cargo nextest run --release`"*) — forks a fresh OS process **per individual `#[test]`**, not per binary. That isolation is uniform across all 613 tests regardless of which binary compiled them. So the "one shared process, 125 tests racing on threads" scenario the brief flagged does not occur under the gate that actually ships.

### 3. Findings

**Finding — `ARM_BUILDS`, a process-global `AtomicUsize`, drives exact-equality correctness assertions across multiple `#[test]` functions in the shared `src/rete/kernel/tests` binary, with its race-freedom resting entirely on runner behavior nowhere stated in the test files.**

- Parallel boundary: none *declared* in the consuming tests — the boundary is the **test runner's own concurrency**, which is exactly the class secare's rune exists for ("some parallel patterns look unsafe but are structurally fine because of an invariant the spell can't see").
- Definition: `src/rete/kernel/arm.rs:728` `pub(crate) static ARM_BUILDS: AtomicUsize`, incremented at `:908` (`ARM_BUILDS.fetch_add(1, Relaxed)`), carries an *unrelated* rune — `// rune:sequi(performance-counter)` at `:727` — addressing production-purity ("carries no domain data"), not cross-test isolation.
- Shared-state touch: read via `Ordering::Relaxed` in **6 `#[test]` functions across 2 files** — `src/rete/kernel/tests/arm_lease.rs:17,30,43` (`fire_rules_reuses_arm_across_fire_and_insert_overlay`), `:110,113,124` (`intern_release_drops_arm_and_next_fire_rebuilds`), `:151,157` (`intern_release_one_session_leaves_the_other`), `:181,184,192` (`intern_overlay_is_not_a_second_lease`), `:263,284` (`scoped_work_with_overlay_reuses_one_build`); and `src/rete/kernel/tests/cascade_cost.rs:348,358` (inside a `for _ in 0..RUNS` loop computing a saturating delta).
- Race class: **lost-update / non-deterministic-count**, if two of these tests ever executed concurrently in one process — `assert_eq!(after, before)`, `assert_eq!(after, before + 1)`, and `"must increment ARM_BUILDS exactly once"` (`arm_lease.rs:255`) all silently break if any *other* test's `fire-rules`/`compile-all` bumps the same counter mid-window.
- Disjoint direction it's missing: none of `collect-then-aggregate` / `index-sliced-writes` / `per-thread-fold-then-reduce` applies — the counter is genuinely one shared cell with no partition, race-free today only because nextest never lets two tests share the process that holds it.
- Why this is a real finding and not noise: this repo has already ruled on the identical shape once, in the same arc. `docs/arc/2026/06/278-rules-engine/BRIEF-signal-tests-cannot-race.md` documents process-global `AtomicBool` signal flags in `src/runtime.rs` racing across `#[test]`s, and the builder's ruling was explicit: *"It is not acceptable that this triggers in `cargo test` … the tests must never have a race, period … Not `green under our runner`. Race-free by construction."* That doc even names the exact trap: *"That reasoning is true for nextest and false for `cargo test`."* `ARM_BUILDS` is the same trap, unfixed, undocumented, and un-runed for *this* concern — it is `#[cfg(test)]`-gated so it cannot be walled the way the signal-flag fix required (a guarded accessor), but nothing records that the safety is runner-dependent either.
- No `rune:secare` exists anywhere in the target (confirmed by the earlier full sweep) — this site is exactly the kind that should carry one, but none of the four listed categories (`disjoint-via-index`, `relaxed-counter`, `read-only-share`, `async-not-parallel`) cleanly fits "safe only because the test runner forks a process per test" — it would need either a new category or, per the sibling doc's own conclusion, a structural wall rather than a rune (nextest could in principle change its default, or a future `cargo test` run of this crate would silently reintroduce the race with no compiler signal).
