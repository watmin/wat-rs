## Finding — claim vs. code (two coordinates), L1

**The claim.** `session.rs:1759-1765` — the module's own doc block, headed "⛔ **BOTH DOORS CALL THIS, AND THAT IS THE WHOLE POINT.**" — states the builder's ruling verbatim: *"the session is the boundary — it may not consume more than the configured amount of memory, 1G by default… insert affects memory just as much."* The identical sentence is repeated at `fire/delta.rs:472-473`, and a third time at `wat/rete/oracle/insert.wat:63-66`: *"The session ceiling is enforced at BOTH doors."* Three shipped sites, same universal claim: the session cannot grow past `max-session-bytes` (default `DEFAULT_MAX_SESSION_BYTES = 1024*1024*1024`, `config.rs:140`).

**What the code actually does.** There are exactly two call sites of `session_ceiling_breach` in the whole target — `fire/delta.rs:715` and, via `check_insert_ceiling`, `insert.rs:173` and `insert.rs:214` — and each is a single check *after* an unbounded amount of work has already completed, not a bound on that work:

- `fire/delta.rs:712-727`: the check runs once, **after** a whole round's alpha/join/accumulate/filter/production passes have all run and after `next_delta` has been fully materialized. `delta.rs:441-443`, in the *same file's* adjacent doc block about the round cap, admits outright: *"One round may still derive without bound — `fanout` derives 40_000 facts in a SINGLE round — and that is a legitimate workload shape this deliberately does not limit."* Nothing connects that admission back to the memory-ceiling promise two paragraphs later.
- `insert.rs:196-215` (`insert_facts_on_session`, the `insert-all` batch door): `vector_concat_inner` fully materializes `new_facts` — the entire batch, concatenated — at line 205, and `check_insert_ceiling` is only called at line 214, *after* that allocation exists. The single-fact door (`insert.rs:150-172`) is the same shape at a smaller scale, by design ("checked AFTER staging on purpose").

So the actual guarantee is "checked at round/batch boundaries," not "may not consume more than 1G." A single fixpoint round or a single `insert-all` call that derives/stages enough facts to itself exceed the ceiling will do so *before* either check has a chance to run — the identical failure mode the ceiling exists to prevent (the 2.5M-facts/4.0GB incident both doc sites cite as the motivating measurement, `session.rs:1763`) can still happen, just one level down: inside one round instead of across many, or inside one `insert-all` instead of across many `insert` calls. No line here is wrong — `session_ceiling_breach` correctly reports the state it's asked about — the gap is in the check's *placement*, which the shipped "it may not consume more than… 1G by default" sentence does not disclose.

- What the inward guard saw here: nothing — `sequi` (state-threading) confirmed the ceiling read is a single clean chain and rowed only the *unrune'd read* (Q1), not this timing gap; `struere`/`conformare`/`probare` did not touch this pair of doc blocks at all; `excusare` weighs runes, and this claim carries none to weigh.
- Severity: **L1** — it contradicts a shipped, explicitly-attributed-to-the-builder claim, at three sites, and (per the ward's own escalation rule) a never-patched artifact can't retract that sentence.
- Closure: not a one-line fix (the four-questions test: this is an *inherent cost*, matching exactly how `delta.rs:441-443` already treats the round-cap's own version of this same gap — "deliberately does not limit"). The right closure is documentation, not code: qualify the three claim sites to say what's actually true — *"checked at round/batch boundaries; a single round's derivation or a single insert-all's batch is not itself bounded and can transiently exceed the configured ceiling before the next check runs"* — and, per the rune's own heavier burden, back it with a `rune:circumspicere(accepted-by-design)` at `session.rs:1759` and `fire/delta.rs:472` naming this file's own `:441-443` as where the bound is disclosed.
