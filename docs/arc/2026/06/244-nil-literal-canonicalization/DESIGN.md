## Why this arc — how the domain was found

Resuming 237.8b (unblocked for `&` since 241.5 `639b4862`), `tests/probe_arc237_8b_defclause_arithmetic.rs` failed — but **not on `&`.** A defclause-bearing program tripped:

```
MalformedForm { head: ":wat::core::nil",
  reason: "Doctrine 1 (arc 242): ':wat::core::nil' is a TYPE keyword, not a value;
           use bare `nil` in value position" }
```

The first read — "stale fixture" — was **wrong**, and correcting it is the spine of this arc. `(:wat::core::defn :user::main [] -> :wat::core::nil nil)` is a VALID 0-ary nil-returning fn: `:wat::core::nil` after `->` is the return TYPE (type position — correct per arc 242), bare `nil` is the body VALUE (value position — correct per arc 242). **The source is right; the substrate is wrong.** (`feedback_nonintuitive_error_is_pivot` — a confusing error is a substrate defect; the move was to attack the substrate, never to "fix" the correct test to match the lie.)

Bisection (`tests/probe_nil_return_value_position_bug.rs`) isolated it: the simple nil-returning fn checks CLEAN; adding a **defclause** to the program makes it fail, with the error span on the *defclause*, not the main fn. The offending `:wat::core::nil` is **synthetic** — generated by the substrate, carrying the defclause's own span.

## The failure class

Two structural facts, both grounded in `src/ast.rs`:

1. **`WatAST::Keyword` is context-polymorphic by design** (ast.rs:48-56): the SAME Rust variant is *"used both as keyword literals … and as keyword-path references (heads of calls, type annotations). Distinguished by context at later passes."* A type keyword and a value literal are the same type; nothing structural keeps a type-keyword out of a value slot. A function `body: Arc<WatAST>` accepts any node. The only objection is the check-time string compare at `check.rs:3373` — *after the fact*, the very level Pattern A forbids us to rely on.

2. **nil is the lone scalar with no `*Lit` variant** (ast.rs:36-46, 120-131): `int / float / bool / string` each have an `IntLit / FloatLit / BoolLit / StringLit` variant AND a `WatAST::int / float / bool / string` constructor. **nil has neither** — it is a bare `Symbol`. So when the substrate needed to synthesize a nil VALUE, there was no constructor to call and no literal variant to reach for. Seven sites improvised `WatAST::Keyword(":wat::core::nil")` — the type keyword — which pre-242 was an accepted nil-value form and arc 242 retired. **The asymmetry created the heresy.**

The seven hand-rolled syntheses —
`closure_extract.rs:1994`; `runtime.rs:2771, 3739, 6548, 17893, 25523`; `check.rs:7442` —
are N copies of one logical act, the exact anti-pattern `ast.rs`'s OWN `children()` comment (ast.rs:158-194) already warns against:

> *"that produces N copies of the same logic and N opportunities for the same bug … the honest fix is at the substrate layer: own [the thing] here, so [callers] can't get it wrong. The bug class is structurally eliminated."*

The author wrote down the cure and had not applied it to nil.

**State to make unrepresentable:** a synthesized nil VALUE expressed as the `:wat::core::nil` TYPE keyword.

## The doctrine — asymmetries meet a very high bar

User direction 2026-06-02: ***"asymmetries must meet a very high bar for acceptance."*** nil-as-bare-`Symbol` while every other scalar is a `*Lit` variant is an asymmetry that never cleared the bar — it merely hid until it cost a four-day detour's worth of confusion. This arc ends it. The bar is not "does it work"; it is "does the shape tell the truth, symmetrically, so the next author cannot be misled."

## The strategy — annihilate the domain (not patch the sites)

1. **Mint `WatAST::NilLit(Span)`** — nil joins `int / float / bool / string` as a first-class literal variant; the asymmetry dies. The parser produces `NilLit` for bare `nil`. `span()` / `children()` / `variant_name()` / `Hash` / `PartialEq` and every downstream match arm gain their nil case (a substrate-as-teacher cascade — the fail-count is the progress meter).
2. **Mint `WatAST::nil()`** — the missing value-constructor; the ONE canonical way to synthesize a nil value.
3. **Sweep every synthesis through it** — the 7 `Keyword` sites plus any non-`Keyword` nil-value patterns the audit surfaces.
4. **Remove the heretical form from existence** — a build-failing gate forbidding `WatAST::Keyword(":wat::core::nil")` construction anywhere in `src/` EXCEPT the parser/lexer (where it legitimately arrives from user source). In *synthesis* it is always the heresy: types are `TypeExpr` (see `ret_type: TypeExpr` at the stub), values are now `WatAST::nil()`. Re-introduction becomes a red build, not a code-review plea — the level-3 the convention could not reach.

The check at `check.rs:3373` is **CORRECT and stays** — `:wat::core::nil` IS illegal in value position. We fix the synthesis; we never weaken the check.
