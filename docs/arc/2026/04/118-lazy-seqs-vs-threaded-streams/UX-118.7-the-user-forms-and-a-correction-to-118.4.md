# ⛔ FIRST — 118.4 GOT `length`/`empty?` WRONG, AND THE STDLIB PROVES IT

118.4 ruled: *"A read-once value gets no cheap structural queries. `length` and `empty?` both refuse
Stream… `measurable()` needs NO CHANGE AT ALL… `Stream => false` is the correct answer for both."*

**Measured today. Neither half is true.**

| | type-checks? | runs? |
|---|---|---|
| `(empty? some-stream)` | ✅ | ✅ returns `false` |
| `(length some-stream)` | ✅ | ⛔ **RAISES** |

```
:wat::core::length: expected Vector<T>, HashMap<K,V>, PersistentMap<K,V>,
PersistentVector<T>, HashSet<T>, or List<T>, got wat::stream::Stream `<lazy-seq>`
```

## Two findings, and the second is a live defect

**1. `empty?` on a Stream works, and the stdlib DEPENDS on it.** `wat/seq.wat:457` — `keep-stream`'s
own body is `(:wat::core::if (:wat::core::empty? s) …)` where `s <- Stream<T>`. Every twin walks a
stream with `empty?`/`first`/`rest`. Refusing it would break the stdlib. The Ruby analogy was sound
as *design taste* and wrong as *description of this substrate*.

**2. `length` is CHECKER-PERMISSIVE, RUNTIME-REFUSING.** It type-checks and then raises — the worst
of both. That is **the third instance today** of the class 279.4 just closed for `interpolate`
(checker admits what the runtime rejects), and the first two were `interpolate` and the `Seqable`
blockers themselves.

## How I got it wrong

I read `measurable() => false` for Stream and **inferred what it gated** rather than testing it. Its
doc says *"`length` / `empty?` — element count"*, so I concluded both refuse. In fact the table
governs one of them and not the other, and the one it governs fails at the wrong layer.

`[[feedback_a_design_sentence_is_not_the_disk]]` — a capability table is a design sentence too.

## The corrected disposition

- **`empty?` over `Seqable`** — keep. Cheap, works, load-bearing for every lazy walk.
- **`length`** — a real defect to fix, not a contract to preserve. Either it accepts a `Seqable` and
  walks (Clojure's `count`), or the **checker must refuse it**. It must not type-check and raise.
  **This is now part of the Seqable work, not out of scope.**

# THE USER FORMS — before and after

## `keep`, verbatim from `wat/seq.wat:463`

```wat
(:wat::core::defclause :wat::core::keep
  ([f <- :wat::core::Fn(T)->wat::core::Option<U>
    coll <- :wat::core::Vector<T>] -> :wat::stream::Stream<U>
    (:wat::core::keep-stream f (:wat::core::seqable->stream coll)))
  ([f <- :wat::core::Fn(T)->wat::core::Option<U>
    coll <- :wat::core::List<T>] -> :wat::stream::Stream<U>
    (:wat::core::keep-stream f (:wat::core::seqable->stream coll)))
  ([f <- :wat::core::Fn(T)->wat::core::Option<U>
    coll <- :wat::core::PersistentVector<T>] -> :wat::stream::Stream<U>
    (:wat::core::keep-stream f (:wat::core::seqable->stream coll)))
  ([f <- :wat::core::Fn(T)->wat::core::Option<U>
    coll <- :wat::stream::Stream<T>] -> :wat::stream::Stream<U>
    (:wat::core::keep-stream f (:wat::core::seqable->stream coll))))
```

★ **Four arms. The bodies are byte-identical.** Not similar — *identical*, character for character.
The arms exist for one reason: to enumerate the types, because the language cannot name the set.
**That is the missing type, rendered as code.**

And it needs a second public verb, `keep-stream` (`seq.wat:454`), whose entire job is to be the
shared body those four arms delegate to.

## After

```wat
(:wat::core::defn :wat::core::keep<T,U>
  [f    <- :wat::core::Fn(T)->wat::core::Option<U>
   coll <- :wat::core::Seqable<T>] -> :wat::stream::Stream<U>
  (:wat::stream::lazy
    (:wat::core::if (:wat::core::empty? coll)
      (:wat::stream::empty)
      (:wat::core::match (f (:wat::core::first coll))
        ((:wat::core::Some v) (:wat::stream::cons v (:wat::core::keep f (:wat::core::rest coll))))
        (:wat::core::None                          (:wat::core::keep f (:wat::core::rest coll)))))))
```

**One `defn`. No arms. And `keep-stream` is gone** — it was only ever the shared body, and now the
body *is* `keep`. The recursion calls `keep` itself, not a twin.

## What a USER writes — unchanged, which is the point

```wat
(:wat::core::keep :my::parse (:wat::core::Vector :wat::core::String "1" "x" "3"))
(:wat::core::keep :my::parse some-list)
(:wat::core::keep :my::parse some-persistent-vector)
(:wat::core::keep :my::parse (:wat::core::map f xs))       ;; a Stream
```

All four work **today** and all four work **after**. The user-facing call site does not move. What
changes is that a user can now write:

```wat
;; MY container joins the language
(:wat::core::defrecord :my::Ring [items <- :wat::core::Vector<wat::core::i64>  head <- :wat::core::i64])

(:wat::core::extend-type :my::Ring :wat::core::Seqable<wat::core::i64>
  (seq [self] -> :wat::stream::Stream<wat::core::i64> …))

(:wat::core::keep   :my::parse my-ring)     ;; ← works. Nothing in core changed.
(:wat::core::filter :my::pred  my-ring)
(:wat::core::remove :my::pred  my-ring)
```

**That is the whole payoff, and today it is impossible at any price.** A user's container can never
join the sequence family, because every verb enumerates a closed list of four builtins.

## And the shape a contributor writes — the rung 278 could not reach

```wat
;; TODAY — nothing stops this. It is quadratic, and it is GREEN.
(:wat::core::defclause :my::stage
  ([coll <- :wat::core::Vector<T>] … (:my::stage (:wat::core::rest coll)))
  ([coll <- :wat::core::List<T>]   … (:my::stage (:wat::core::rest coll))))

;; AFTER — the per-container arm has NO FORM. There is one shape and it is the fast one.
(:wat::core::defn :my::stage<T> [coll <- :wat::core::Seqable<T>] … )
```

278 named this gap in its own stone: *"nothing stops a new wat-level stage with per-container arms
and a `rest`-walk tomorrow, and it would be quadratic and green."* `Seqable` is what turns that
convention into a wall.

## ⚠ What this changes about the build order

`length` moves **into** scope: it is a checker/runtime divergence, not a contract. And
`measurable()`'s doc comment is wrong about what it gates — it claims `length` **and** `empty?`,
while `empty?` is unaffected by it.

Every other measured claim in `118.4` and `118.6` stands. The `length`/`empty?` section of 118.4 is
superseded by this file.
